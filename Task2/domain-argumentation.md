# Задание 2. Домены, потоки данных и обоснование

## 1. Разделение на домены

| Домен | Назначение | Почему отдельно от DWH |
|--------|------------|-------------------------|
| **Клиники и операции** | Расписание, ресурсы, клинические операции, интеграция с оборудованием; операционные данные в своём ODS | Скорость изменений в «поле» не должна упираться в монолит отчётности; новая логика живёт в сервисах и событиях, а не в хранимках DWH |
| **Финтех** | Продукты банка, платежи, кредиты, лимиты; нормативные и транзакционные данные в ODS финтеха | Финансовый регулятор и релизный цикл банка требуют автономности; интеграция с аналитикой — через контракты (события, CDC), а не через доработку ядра DWH |
| **ИИ и клиническая аналитика** | Модели, инференс, оркестрация; доступ к разрешённым медицинским срезам по политике | ИИ меняется часто; смешивание с корпоративной отчётностью повышает риск и задержки; граница с витриной данных зафиксирована политикой (медкарты не в BI) |
| **Платформа данных и витрины** | Lakehouse, витрины, KPI, семантический слой, портал самообслуживания | Это **потребление** для отчётности, а не место для операционной бизнес-логики доменов; расширяется витринами и пайплайнами, а не процедурами внутри старого DWH |
| **Интеграция и партнёрский контур** | API-шлюз, шина событий, адаптеры к фарме и производителям электроники | Партнёры подключаются через стандартизованный контур без прошивки каждого изменения в SQL Server 2008 |
| **Легаси-DWH (переходный)** | Исторические данные, остаточные отчёты; мост (CDC) в платформу данных | Явно выделен как **источник для миграции**, куда не добавляется новая логика |

**Для кого нужен какой домен**

- **Клиника:** домен «Клиники и операции» + при необходимости ИИ по контракту; аналитика по KPI — через «Платформу данных», без сырых медкарт в витрине (по политике компании).
- **Финтех:** домен «Финтех» + потоки в витрины для управленческой и продуктовой аналитики.
- **ИИ:** домен «ИИ» с отдельным хранилищем артефактов; входы данных — по согласованным контрактам из ODS клиник, не из витрины BI.
- **Будущие партнёры (фарма, электроника):** домен «Интеграция и партнёрский контур» как единая точка каталогов, заказов, лимитов и событий с последующей маршрутизацией в финтех и клиники.

## 2. Логика разделения

1. **Разные скорости жизни:** клиника, банк и ИИ имеют разные циклы релизов и регуляторные рамки; общий DWH как место новой логики выравнивает всех «по самому медленному» и тормозит вывод продуктов.
2. **Разные модели данных:** финансовые проводки, операционные сущности клиники и признаки для моделей — не одна универсальная схема; доменные ODS и контракты событий снимают потребность тащить всё в один физический узел.
3. **Снижение связности:** новые финтех-сервисы и партнёрские сценарии подключаются через шину и API; платформа данных **подписывается** на события и реплики, не требуя изменений ядра DWH.
4. **Безопасность и комплаенс:** граница между клиническими данными для ИИ и агрегатами для отчётности управляется политиками и отдельными потоками на DFD, а не одной «общей таблицей».

## 3. Преимущества для бизнеса

| Эффект | Как достигается |
|--------|------------------|
| **Ускорение вывода продуктов** | Команды финтеха и ИИ выпускают фичи в своих доменах; аналитика потребляет стабильные контракты (события, витрины), не блокируя релизы SQL/DWH |
| **Меньше зависимости от DWH** | Новая логика не пишется в хранимках и процедурах монолита; DWH остаётся источником истории на переход, а рост — за счёт lakehouse и доменных пайплайнов |
| **Независимое развитие направлений** | Отдельные ODS, отдельные команды владельцев данных, интеграция через шину и платформу данных |
| **Масштабирование под партнёров** | Фарма и электроника стыкуются к интеграционному контуру; не требуется каждый раз менять схему центрального хранилища |
| **Предсказуемая отчётность** | Платформа данных строит витрины и KPI из потоков и CDC, разгружая операционные системы и легаси-DWH от ad-hoc нагрузки |

## 4. Связь DFD с бизнес-сценариями

- **Интеграция нового финтех-сервиса:** потоки **P2 → D_Ev → P_Data**; сервис публикует события, витрины обновляются по конвейеру без доработки DWH.
- **ИИ для анализа медицинских данных:** поток **D_Clin ⇢ P_AI** по контракту и политике; результаты могут идти обратно в операции (**P_AI ..> P_Clin**); витрина отчётности (**P_Data / D_LH**) не обязана содержать сырые медкарты.
- **Партнёры:** **E_Pharma / E_Dev → P_Int** с дальнейшей маршрутизацией на финтех и клиники и в шину для аналитики.
