# Задание 1. Проблемные места и приоритизация

## 1. Проблемные места текущего ландшафта (as-is)

| № | Проблемное место | Суть | Какие бизнес-сценарии страдают |
|---|------------------|------|--------------------------------|
| P1 | Монолитный DWH (SQL Server 2008) как «центр тяжести» | Бизнес-логика и отчётность завязаны на одно хранилище; объём — сотни ТБ; устаревшая СУБД | Быстрая отчётность; управленческие решения; планирование инвестиций и филиальной сети |
| P2 | Долгое построение сложных отчётов (часы) | Много трансформаций «на лету», конкурирующая нагрузка с операциями | Оперативное управление; реакция на рынок; согласование с регуляторами по срокам |
| P3 | ESB (Apache Camel) как узкое место интеграции | Синхронные цепочки, сложность сопровождения, риск деградации при росте трафика | Независимый выпуск фич финтеха и ИИ; подключение новых партнёров (фарма, оборудование) |
| P4 | Раздельные потоки медицинских данных (DWH ↔ оператор vs ESB ↔ ИИ) | Дублирование, рассинхрон, сложность единой картины по разрешённым срезам | Качество клинического сервиса там, где нужна согласованность; затраты на согласование данных между командами |
| P5 | BI поверх DWH с сильной кастомизацией | Прямые тяжёлые запросы к DWH, хрупкость при изменениях схемы | Надёжность корпоративной отчётности; скорость изменения KPI при новых продуктах |
| P6 | Риски ИБ и комплаенса на старом контуре | Устаревший стек, сложность аудита и геораспределения | Финансовые сервисы (лицензия банка); работа с чувствительными данными |
| P7 | Вынос новой бизнес-логики в DWH по инерции | Замедление time-to-market новых доменов | Масштабирование на новые бизнесы; выручка от новых продуктов |

## 2. Приоритизация: матрица Эйзенхауэра

Оси: **срочность / влияние на цели бизнеса** (выручка, time-to-market, качество мед. и фин. сервисов).

| Квадрант | Проблемы | Обоснование связи с бизнесом |
|----------|----------|------------------------------|
| **Сделать немедленно** (срочно + важно) | P2, P6 | Без приемлемого времени отчётности страдают решения руководства; без ИБ/комплаенса — недопустимый риск для банка и медицины. |
| **Запланировать** (не срочно + важно) | P1, P5, P7 | Стратегически определяют выручку и TTM через платформу данных и доменную автономию; эффект через кварталы, но без этого цель «через год» не достижима. |
| **Делегировать / укоротить** (срочно + менее важно) | P4 | Важно для согласованности, но часть может решаться контрактами данных и постепенной синхронизацией, не блокируя первый релиз витрины. |
| **Не делать сейчас / минимизировать** (не срочно + не критично в первую очередь) | — | Все перечисленные проблемы важны; «хвост» — точечная оптимизация отчётов, не меняющая архитектуру. |

## 3. Приоритизация: MoSCoW

Связь с целями: **выручка и новые продукты**, **скорость выхода на рынок**, **качество фин. и мед. сервисов**, **масштабирование под новые бизнесы**.

| Приоритет | Проблемы / темы | Комментарий |
|-----------|-----------------|-------------|
| **Must have** | Сократить время получения ключевой отчётности (P2) за счёт витрин и семантического слоя; обеспечить ИБ и аудит на целевом контуре (P6); не смешивать в витрине сырые медкарты с политикой компании (ограничение scope — из вводной) | Без этого бизнес не получает обещанный портал самообслуживания и недопустимы риски по регуляторам. |
| **Should have** | Разгрузить монолит DWH (P1) через lakehouse и мост; увести BI на семантический слой (P5); ограничить новую логику в DWH (P7) в пользу доменов | Прямо бьёт по TTM и стоимости владения данными. |
| **Could have** | Усилить согласованность медицинских потоков (P4) там, где это нужно для продуктов, не нарушая границы доменов | Улучшает качество сценариев ИИ/клиники, но может идти итерациями. |
| **Won’t (на первом году)** | Полный отказ от легаси без моста; «большой взрыв» замены ESB без поэтапной миграции на события и API | Сохранение переходного легаси допускается по вводной; полная замена — за горизонтом первого года. |

---

## 4. Сводная последовательность (связь методов)

1. **Эйзенхауэр:** в фокусе квартала — время отчётности и комплаенс (P2, P6); параллельно старт архитектурных работ по P1, P5, P7.  
2. **MoSCoW:** must — витрина + безопасность + границы данных; should — платформа аналитики и доменная логика вне DWH; could — выравнивание потоков медданных; won’t на год — тотальное уничтожение легаси без эволюции.
